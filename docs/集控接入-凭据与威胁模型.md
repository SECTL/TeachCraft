# 集控接入：凭据与威胁模型

> 2026-11-16 · 回答一个具体问题：**源码全公开，集控安全吗？需要 GitHub Secrets 藏平台 ID 吗？**
> 结论先说：**不需要藏，但需要先修三处。** 这不是「公开也没关系」，而是「公开+修好」才没关系。
> 事实依据：`D:\Documents\SECTL-One-Stop` 与 `D:\Documents\TeachCraft` 的仓库扫描（含 731 个历史提交）。

---

## 一、GitHub Secrets 藏客户端常量：零收益

这个问题已经定论，不再讨论：

| 想藏的东西 | 实际情况 | 结论 |
| :--- | :--- | :--- |
| 地点 ID `SC-K7Q2M9` | 协议 §1 明确标注「❌ 公开」。它是「哪个学校」的地址，不是凭据 | 藏了也没有意义 |
| 平台 ID `teachcraft` | 服务端 `PLATFORMS` 表里的一个键名 | 同上 |
| `device_secret` | 每台设备接入时**现场换发**，64 字符 base64url，服务端只存 sha256，明文只回一次 | **不在源码里，也不该在任何 Secret 里** |

**GitHub Secrets 的实际能力**：让值不进仓库、在 CI 注入环境变量。它挡不住任何人从二进制里挖——凡是客户端要用的值，编进去就等于公开。

把它用在客户端常量上，代价是**构建不可复现、开源状态下根本无法编译**，换来的安全性是零。

> 一句话：用工程成本买一个不存在的安全性。

### Secrets 应该管什么（现状已经对了）

| 仓库 | Secret | 现状 |
| :--- | :--- | :--- |
| TeachCraft | 无 | CI 不用任何 secret（`grep secrets. = 0`）。客户端本来就不需要秘密 |
| SECTL | `APPWRITE_API_KEY` | 走 `secrets.APPWRITE_API_KEY`，正确 |
| SECTL | `CONTROL_HUB_ADMIN_TOKEN` | 从环境读、无硬编码回退、缺失时 fail-closed（503）。正确 |
| SECTL | `DEPLOY_SSH_KEY` | 走 secrets，正确 |

`VITE_*` 那一批确实在 Secrets 里，但它们是**注入前端产物的公开值**（Appwrite project id、bucket id），不是秘密——放 Secrets 只是为了不同环境用不同值。

## 三、⛔ 三处必须先修：公开源码的前提是「不需要再改」

对抗审查的核心结论，逐条核实过：

### 3.1 吊销不即时生效（最严重）

**事实**：`api.mjs:2708` 删除设备只调 `store.deleteDevice()` 再写审计，**不调 `hub.revokeDevice()`**；`rotate-secret` 同样不踢连接。`hub.mjs` 的 `_onClassSelect` / `sendCommand` 全看内存里的 `peer.authed`，`hello` 之后从不复查 secret。

**后果**：管理员从网页删掉一台设备，那条 WebSocket **仍然占着班、仍然能收指令**，直到它自己断线重连才失败。物理接触过教室机的人可以在原连接上继续控制那个班，而管理员看到的是「已删除」。

**修法**：`delete` / `rotate` 一律走 `hub.revokeDevice()`（发 `evicted` + 关闭码 4003）；每次占班、每条指令复查 secret；比对改 `timingSafeEqual`。

> 这一条排在所有安全措施之前。**吊销失效的时候，限速再严也没用。**

### 3.2 限速的 IP 可伪造，配置也没落地

**事实**：

- `api.mjs:671` 的 `clientIp()` 读 `x-forwarded-for` 并取**最左**元素——那是客户端可任意伪造的头。
- `deploy/nginx/sectl.cn.conf` 里**一个 control 相关 location 都没有**，而 `README.md:238` 声称「已加进该文件、线上一致」。
- 限速计数在 `api.mjs:86-88` 的进程内 Map，Hub 重启/发版即清零。

**后果**：每 IP 10 次/分形同虚设（改个头就是新 IP），兜底只剩与 IP 无关的每地点 50 次/时，而这层随重启消失。

**修法**：nginx 配 `limit_req`，XFF 只信受信代理（`real_ip` 白名单）；失败计数落库；成功时把该 IP/地点计数归零。

> 绝对风险仍低（配对码 8.5e11 空间），但**不能拿限速当安全依据**。

### 3.3 数据面有两处真实泄露路径

| 路径 | 事实 | 后果 |
| :--- | :--- | :--- |
| `seats` 含 `studentName` 而 `seats.read` 只要 viewer | `api.mjs:3224` + `authz.mjs:91` | **给某人 viewer 等于给他全校学生座位表** |
| `device/homework-assignments` 允许 secret 放 query | `api.mjs:1496` | secret 落进 nginx access log |

**修法**：`seats` 去掉 `studentName`（或 `read` 抬到 operator）；禁止 secret 走 query。

> 这两条对我们尤其重要——知微接入后如果也要传座位，必须先把这条修掉。

## 六、结论

**「地点 ID 本该公开」——对，我没在担心它。** 上一轮我把主次讲反了，抱歉。

真正要守的不是「藏什么」，而是三件事：

1. **仓库里永远没有真凭据**——这条现在成立（731 个提交扫过，零命中），但要靠 `.gitignore` 补洞 + 提交前拦截维持。
2. **服务端把吊销做对**——现在没做对，这是唯一挡在「可以放心公开」前面的硬缺陷。
3. **数据面不多传**——`seats` 里的 `studentName` 要拿掉，知微自己也别往上报姓名。

至于 GitHub Secrets 藏平台 ID：**不做，不遮蔽，不动。** 它只会让构建不可复现，买不到任何安全。
